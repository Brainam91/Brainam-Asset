The flow

1Customer signs up
Email + name + phone + business name (and optional Google OAuth). Two collections written: full profile on User, identity snapshot on Workspace.
server/routes/auth.ts POST /api/auth/register server/routes/auth.ts:23–36 ensureDefaultWorkspace() server/models/User.ts full profile server/models/Workspace.ts identity snapshot
2Customer picks account type
Individual / team / business etc. Writes to Workspace (not User). The frontend's Onboarding screen calls a tiny POST.
client/src/pages/OnboardingProfile.tsx server/routes/onboarding.ts:206 POST /api/onboarding/type server/models/Workspace.ts accountTypes, primary
3Tara conversation — questions, text, voice, files
Tara reads what's on Workspace, asks the next question, customer's reply (typed or transcribed from Whisper or extracted from PDF) lands back on the same Workspace.
client/src/pages/OnboardingProfile.tsx server/routes/onboarding.ts /turn /transcribe /extract-file server/services/tara.ts prompt + reply server/models/Workspace.ts conversationHistory[], whisper[], structuredBrief server/models/WorkspaceKnowledgeFile.ts source='tara' server/models/WorkspaceKnowledgeChunk.ts
Correction to step 3 of the original sketch: Tara's chat transcript lives INLINE on Workspace.conversationHistory[]. There's no separate transcript model. Audio + document text DO get their own collections (WorkspaceKnowledgeFile + WorkspaceKnowledgeChunk).
4Customer adds knowledge from the dashboard
PDFs, links, drag-and-drop. Same plumbing as Tara's uploads — just a different source tag.
server/routes/workspaceKnowledge.ts POST /api/knowledge server/models/WorkspaceKnowledgeFile.ts source='dashboard' server/models/WorkspaceKnowledgeChunk.ts server/services/ChromaService.ts vector embeddings
Correction to step 4 of the original sketch: Knowledge is NOT a field on Workspace. It's two dedicated collections (WorkspaceKnowledgeFile + WorkspaceKnowledgeChunk) scoped by workspaceId. Both sources (Tara + dashboard) share the same collections.
5Customer clicks "Build agent"
Wizard opens. They pick the trigger app first (chat / email / webhook / schedule), then name the agent, then Jiya does a short clarifying chat, then Divya writes the basePrompt asynchronously.
client/src/components/AgentSetupWizard.tsx server/routes/agents.ts POST /api/agents/reserve server/routes/agents.ts POST /api/agents/setup server/services/jiya.ts clarifying chat server/services/divyaFromDigest.ts writes basePrompt
6Agent record is created
The agent's name, model, base prompt, capability flags, schedule fields, etc. all land on a single document.
server/models/AgentConfig.ts the agent
7Trigger row is dual-written
Whichever trigger the customer picked, /setup writes the per-trigger field on AgentConfig AND upserts a row on the canonical Trigger collection. Both collections agree.
server/models/AgentConfig.ts chatSlug / webhookToken / emailAddress / scheduleEnabled server/models/Trigger.ts { agentId, type, slug, enabled }
Correction to step 7 of the original sketch: Trigger pick goes to BOTH stores, not just Trigger.ts. AgentConfig holds the per-trigger fields (chatSlug, webhookToken, emailAddress, scheduleEnabled) as the read primary; Trigger holds the canonical row that's mainly used for cross-cutting features like deletion + audit. See per-trigger lookup order below.
8Inbound event fires the agent
Customer's URL gets visited, webhook delivered, email forwarded, or cron tick happens. Each trigger has its own public route, its own lookup, its own hardened gate stack.
server/routes/publicChat.ts POST /api/chat/:slug server/routes/brainamWebhook.ts POST /api/webhook/:token server/routes/emailWebhook.ts POST /webhook/email server/routes/agents.ts fireScheduledAgent() — cron callback server/services/AgentRuntime.ts the LLM call server/services/ChipService.ts wallet metering
Correction to step 8 of the original sketch: AgentConfig does NOT read from Trigger — it's the other way around in some cases. Chat/Email/Schedule routes look up only AgentConfig (chatSlug / emailAddress / triggerType='schedule'). Webhook is the one trigger that also consults Trigger, and only as a fallback when AgentConfig misses. See the per-trigger table.

The four triggers — read order on the inbound route

Brainam Chat

AgentConfig only · slug = customer-picked kebab-case
server/routes/publicChat.ts AgentConfig.chatSlug

Brainam Webhook

AgentConfig primary → Trigger fallback · slug = 160-bit opaque token
server/routes/brainamWebhook.ts AgentConfig.webhookToken Trigger.slug (type='webhook')

Brainam Email

AgentConfig only · slug = local part of local@mail.brainam.ai
server/routes/emailWebhook.ts AgentConfig.emailAddress

Brainam Schedule

No inbound lookup · cron registered at startup from AgentConfig.find({ triggerType:'schedule' })
server/routes/agents.ts registerAgentSchedule / fireScheduledAgent AgentConfig.scheduleTime, scheduleFrequency, scheduleEnabled
